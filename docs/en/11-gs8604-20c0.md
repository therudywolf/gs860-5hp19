# 11 · GS8.60.4 (software 20C0, 512 KB): what is known and how it differs from GS8.60.0

Documents 01–10 describe the GS8.60.0 (software 19C0 / 19D0, 256 KB). This one is about the **GS8.60.4** with program **20C0** (512 KB image, program label `B223K_0520C0` at `0x6FF7C`, calibration label `B223K_0520C06440` at `0x7FFCE`). Everything below comes from two factory 20C0 images (a dump of an E46 and a factory file of the same calibration: they differ only inside the programming journal `0x4440–0x6089`, whose content and the unit serial are not reproduced here) and from a comparison with 19D0 by the method of document 10: capstone m68k, an own scan of address references, the pointer structures parsed from the image itself. Every instruction address in this document was re-checked against the image on 27.09.2026. Sections 5, 9, 10, 13 and 14 were extended on 30.09.2026: record field roles proven by the 20C0 code, all 20 record roots, the RAM of the execution module, the candidate `0x1AAFC` checked.

The confidence levels are those of `catalog/gs8604_20c0.json`: **proven** — a 20C0 instruction reads the address (the instruction address is given); **structure** — the same place in a structure as in 19D0 (catalog slot, record column, constant block) with the role proven there, the 20C0 read not examined separately; **shape** — a table header and axes or the pointer packing prove the size, the role is not established; **hypothesis** — not proven. What is not proven for 20C0 is called that.

## 2. Checksums (proven)

Three CRC-16/XMODEM sums (polynomial `0x1021`, initial value 0, table `0x3EE2` inside the image, equal to the 19D0 table at `0x3EDA`). The handler of DS2 command `0x0A` (`0x1392`) computes them with the routine `0x223C`; the right bound is excluded, the sum is stored big-endian.

| Region | Range | Stored at | Handler instructions |
|---|---|---|---|
| loader | `0x00000–0x043FF` | `0x5FFE` | `0x13FE cmpi.l #$4400`, `0x141A lea $5ffe` |
| program | `0x08000–0x6FF7B` | `0x6FFFE` | `0x143E move.l #$8000`, `0x1474 cmpi.l #$6ff7c`, `0x1490 lea $6fffe` |
| calibration | `0x70000–0x7FFCD` | `0x7FFFE` | `0x14B6 move.l #$70000`, `0x14EC cmpi.l #$7ffce`, `0x1508 lea $7fffe` |

The routine `0x223C` is called only by three `JSR`s of this handler (`0x13F6`, `0x146C`, `0x14E4`); there is no other call or pointer to it in the image: like 19x0, the unit checks the sums **only when a tester asks**, not at start-up. The result goes to bits 0–2 of `0xFFFF8ABF` and into the reply. Both factory images match on all three sums. Check and recompute: `python3 tools/gs860_crc.py check image.bin`, `gs860_crc.py fix edited.bin fixed.bin` (after any edit in TunerPro).

The program region starts at `0x8000`, so **the ROM constants `0x08000–0x10000` (gear ratios, transition types, arbiter) belong to the program sum**, not to the calibration sum.

## 3. Calibration: zones, pointer catalog, objects

The table format is that of 19x0 (document 01 §2): `[u16 nx][u16 ny][X axis][Y axis][data]`, big-endian, axes strictly increasing. The scanner `egs_tables.py scan` finds **614 tables** in 20C0 (50 in the first zone, 564 in the second, 18,206 bytes); five scanner "tables" (`0x7104E`, `0x79A76`, `0x7A608`, `0x7A854`, `0x7B2FB`) are false — a record field points inside them — and are not in the catalog.

Pointer catalog `0x71BC2`: **43 slots** (the last at `0x71C6A`, then `0xFF`; earlier notes said "44" — recounted from the image). All 43 slots are read by code (the reading addresses are in the catalog). The 19D0 slots 0–5 (`0x8142`, `0x81A0`, `0x81B2`, `0x8226`, `0x824A`, `0x8EAC`) are not in the 20C0 catalog: the code takes the same tables directly (`0x7013A` at `0x25226`, `0x70196` at `0x1AAFC`, `0x701A8` at `0x1AB6C`, `0x70210` at `0x1173E`, `0x70236` at `0x1CDCC`, `0x70EF8` at `0x219E0`). 19D0 slots 6–41 = 20C0 slots 0–35, 42–47 = 37–42; slot 36 (`0x71C52 → 0x71AD0`) is new.

The shift-automaton records (§9) contribute another 1280 pointers into the calibration, all 20 record roots together 2137 objects of the zone `0x78000–0x7D858`; the type of every object is determined **by packing**: an object ends where the next pointer target begins (1 byte — u8, 2 — u16, otherwise the single table-header reading whose size equals the gap). Where an object is found both by the scanner and by packing (590 cases) the readings agree.

Result in `catalog/gs8604_20c0.json` (since 30.09.2026): **1772 entries** (1067 tables + 705 constants): 1551 proven by code, 19 by structure, 201 shape only, 1 hypothesis (`0x708A8`, as its 19D0 pair). Before 30.09.2026 there were 981 entries (78 / 70 / 832 / 1): the record field roles were not proven then and the scalar record fields were not in the catalog. The XDF `xdf/GS8604_20C0_Full512K.xdf` and the English `xdf/GS8604_20C0_Full512K_EN.xdf` are generated from the catalog by `tools/make_xdf.py`; categories 01–03 and 12–16 match the 19D0 ones, 04–10 are the record sets and the root `9804` with roles, 11 the records and roots without a role.

## 4. Shift-point matrices (proven, except the roles)

16 tables 2D8 8×11 at `0x7120E + k × 0x70` (k = 0…15, data from `0x71225 + k × 0x70`), catalog slots 14–29. The Y axis is the gearbox pedal (`0xFFFF912B`), row 255 is kickdown. Columns 1–4 are the upshifts 1-2, 2-3, 3-4, 4-5, columns 5–8 the downshifts 2-1, 3-2, 4-3, 5-4: column and program come from the gear record `[down to][up to][down column][up column][down program][up program]` at `[0xFFFF8A2C + 4 × program] + 6 × (gear − 1)` (`0x205B4–0x205CE`); all 16 programs have the columns in this order. In 20C0 every program has a record for the sixth gear.

**The unit is output shaft rpm / 32**, as in 19D0 (document 02 §3). The speed function `0x20C5A` matches 19D0 `0x24E82` instruction for instruction: filtered output shaft `0xFFFF8D18` (`0x20D2E`, filter weights `0x70FC4 / 0x70FC5` = 9 / 1), `lsr.w #5` (`0x20D36`), stored in `0xFFFF9138` (`0x20D38`). Channel-0 constant: 19D0 keeps K = 1,666,666 at `0x116C8`, 20C0 computes K = 60,000,000 / [`0x70302`] = 60,000,000 / 36 (`0x1E3D6–0x1E3EE`); the limits 33 / 8160 are at `0x70300` / `0x702FE` (19D0 `0x116CC` / `0x116CE`); channel 1 (turbine) has 18 pulses, `0x7096C`. Byte 2 of the `0B 03` frame is the same `0xFFFF9138` (`0x1438E`).

Comparison. Upshift `0x2061E`: the matrix threshold **plus `0xFFFF9143`** (`0x20660–0x20670`) against `0xFFFF9138` (`0x20688–0x20692`: shift when `9138 ≥ threshold + 9143`). The addition is set by the new function `0x20D8E`: with `[0xFFFF91B3] = 2` it is the byte `0x70B98[gear − 1]` = 4 / 2 / 2 / 5 / 0 / 4, otherwise 0. The meaning of `[0xFFFF91B3] = 2` is not established. Downshift `0x206A2` matches 19D0 `0x24ADE`: `0x206E4 cmp.b $ffff9138` with the threshold minus `0xFFFF9144`.

Matrix selection by program number (`0x20768`, branches onto the catalog slots) is the same as 19D0 `0x24BA4`:

| program | P0 | P1 | P2 | P3 | P4 | P5 | P6 | P7 | P8 | P9 | PA | PB | PC | PD | PE | PF |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| matrix k | 14 | 6 | 11 | 15 | 0 | 1 | 2 | 13 | 9 | 12 | 5 | 10 | 7 | 8 | 4 | 3 |

The gear records live in the calibration (list `0x08744`, bank 7 = `0x70000`): P0 `0x70FA0`, P1 `0x701CE`, P2 `0x70E72`, P3 `0x70FE4`, P4 `0x70000`, P5 `0x70024`, P6 `0x70048`, P7 `0x70F7C`, P8 `0x70A68`, P9 `0x70D96`, PA `0x700F2`, PB `0x70A32`, PC `0x702CC`, PD `0x702A8`, PE `0x700A0`, PF `0x7007C`. They show which matrices are reachable at all: the PC records in 20C0 name program 6 (matrix k2), not 12 as in 19D0, so **matrix k7 (`0x7151E`) is never selected by the shift code**. Program PA uses k14 in gears 1–4 and k5 in 5th, as in 19D0.

Gear ratios: `0x0E0D2` = 3665, 3665, 1999, 1407, 1000, 742, 742, 4096, indexed by gear code, read by one function `0x41648` (in 19D0 `0x12F9C[gear − 1]` is read directly in 24 places). Gears 1–5 are the same numbers: one matrix unit = 117.3 / 64.0 / 45.0 / 32.0 / 23.7 turbine rpm in 1st–5th.

Matrix data: the axes of all 16 pairs 19D0 / 20C0 are identical, the data match for k9, k12, k13. Example PB (k10), pedal 255, columns 1–8: 19D0 `49 95 137 200 41 86 129 189`, 20C0 `44 102 151 211 41 93 138 203`; the k10 upshifts do not depend on the pedal and with the 20C0 ratios give 5160 / 6525 / 6799 / 6752 turbine rpm (no slip). Minimum gear on manual downshifts `0x70B3C` (16 × 5, `0x1961C`): P0 `0 41 86 130 184`, PB `0 41 105 153 207`.

## 5. A road log and the matrix roles (hypothesis)

The S / M / D roles for 20C0 are **not proven**. What is known:

- In the left gate program PB (matrix k10) is engaged at once, without touching +/− (§7); in a road log of 23.09.2026 (a car with 20C0, `0B 03` frames every 0.62–1.62 s) byte 22 became `0xB2` in the same frame as the gate flag in byte 18, and every shift in the gate ran under PB.
- Of 13 upshifts under full pedal in the gate, the 1-2 agrees with the k10 threshold (n_out/32 = 52 at a threshold of 44), while **11 upshifts 2-3, 3-4 and 4-5 were already in progress** (byte 21 bit 7 = "shift in progress", `0x1A2A0`) while n_out/32 was **below** the k10 threshold:

| shift | pedal | engine rpm | n_out/32 before → after | k10 threshold (turbine) |
|---|---|---|---|---|
| 2-3 | 254 | 6048 | 92 → 98 | 102 (6525) |
| 2-3 | 254 | 6336 | 96 → 102 | 102 |
| 3-4 | 254 | 6208 | 136 → 143 | 151 (6799) |
| 2-3 | 254 | 6304 | 95 → 101 | 102 |
| 3-4 | 254 | 6400 | 140 → 142 | 151 |
| 4-5 | 219 | 5248 | 160 → 160 | 211 (6752) |
| 3-4 | 254 | 6272 | 135 → 137 | 151 |
| 4-5 | 243 | 5728 | 177 → 177 | 211 |
| 2-3 | 254 | 6176 | 95 → 104 | 102 |
| 3-4 | 241 | 6048 | 131 → 133 | 151 |
| 3-4 | 254 | 6368 | 135 → 138 | 151 |
| 4-5 | 254 | 6208 | 195 → 196 | 211 |

The addition `0xFFFF9143` only raises the threshold, so these upshifts were not caused by the comparison `0x2061E`. The engine-rpm upshift request `0x105DE` (§7) was inactive in that run: frame byte 6 = `[0xFFFF8C8C] + 15` = 138–158, the condition `[0xFFFF9066] ≤ 40` was never met. The frame carries neither a manual shift request nor the flags of the arbiter records `0x1F200`, and the lever contacts (byte 18, bits 1–3) cannot catch a short tap at a 0.7 s step. **Not explained.** Possible causes: a driver request (arbiter records 1, 2, 25 are set by `0x2042A`) or another arbiter record. Until a run with markers (D full throttle, S full throttle, M to the limiter without touching the lever) and RAM reads through `0x06`, the 20C0 matrix roles are a hypothesis. `egs_tables.py verify-shift` on 20C0 assigns roles by shape only and says so.

**The candidate `0x1AAFC` was checked on 30.09.2026 and does not explain the upshifts.** The 20C0 counterpart of 19D0 `0x81A0 / 0x81B2` is the pair `0x70196` and `0x701A8` (2D8 4×2, X = engine speed / 32 `[0xFFFF9140]`: 0 / 5312 / 5344 / 6208 rpm, Y = branch `[0xFFFF917F]`, Z = 15 / 15 / 30 / 30 and 15 × 8). All five reads (`0x1AAFC`, `0x1AC06`, `0x1ACE8`, `0x1AB6C`, `0x1AD7A`, call `0x19BD2`) compare the result with the **pedal rate** `[0xFFFF911E]`: `0x1FFCC–0x1FFE6` maps the pedal `[0xFFFF912A]` = `[0xFFFF911B]` (`0x1CDE6`) through the slot 1 table (`0x71064`) into `[0xFFFF906E]`, and `0x20000–0x20020` computes `|Δ[0xFFFF906E]| × 30 / Δt`. Exceeding it sets `[0xFFFF90B5] / [0xFFFF90B4] / [0xFFFF90B3]` and bit 7 of `[0xFFFF9061]` (`0x1AB24–0x1AB52`); no code tests bit 7 (the whole byte stands in the pointer lists `0xAD02–0xAE3E`, whose purpose is not analysed). In 7 of the 11 upshifts of the table above the pedal stood at 254 in every frame before the shift and in the frame where it was already running (4 frames, about 2.5 s, step 0), i.e. a pedal rate of 0 against a threshold of 30: the block did not fire. The other four cannot be decided at a 0.6 s frame step: in one the pedal reached 254 1.9 s before the shift, in one it moved between 219 and 247, in two it started to drop (254 → 243 and 241) in the shift frame. The cause of the 11 upshifts remains **not explained**. The per-upshift table (engine / 32, value of `0x70196`, pedal by frame) is in a WOLF4X project report and is not published here (a third party's car log).

## 6. TCC lockup, upper level (proven)

The 19D0 pair `0x29056` (document 03 §2) is the 20C0 function `0x2547E` with two checks.

- Gear mask `0x7096E` = `0x007E` (`0x25494 and.w`): lockup allowed in 1st–6th (19D0 `0x8978` = `0x003C`, 2nd–5th). The inhibit by an error with bit 8 is checked through `0x1532A` (`0x254B8`).
- **First check `0x255F2`**: group = byte `[0x70970 + 6 × program + gear − 1]` (`0x255F6–0x2561A`), 0 = no decision; thresholds `0x71996` 30×9 (slot 35, columns (group − 1) × 3 + 0…2) and `0x71AD0` 6×9 (slot 36, columns 30–35 = groups 11–12); compared with n_out/32 `0xFFFF9138`, hysteresis `0x70BB0` = 3. Rows are the gearbox pedal (0 / 5 / 46 / 59 / 72 / 224 / 230 / 240 / 255). Groups P0–P3: `11 4 1 2 3 0` (gears 1–6), PB: `0 5 8 9 10 11`.
- **Second check `0x257C2`, 20C0 only**: group `[0x709D0 + 6 × program + gear − 1]` (`0x257E4`), thresholds are the bytes `0x70BB2` (`0x25812`, index (group − 1) × 3 + 0…2) = 107 / 111 / 114 / 88 / 91 / 103 against **turbine / 32** `0xFFFF9145` (`0x2583A–0x2583E`), hysteresis `0x70BB1` = 3. Groups: P2, P3 — `0 2 2 2 2 0`, P4–P6 — `0 1 1 1 1 0`, PC, PD — `2 2 0 0 0 2`, the rest zero.
- The results of the two checks (0 / 1 / 2 each) are merged by the ROM table `0x0AF1E` 3×3 = `0 1 2 / 1 1 2 / 2 2 2` (`0x254FA`) into the request `0xFFFF91B4` (19D0 pair `0xFFFF91F9`). Hold by gear `0x70F20` = `0 6 6 6 6 0` (`0x25574–0x2557A` → `0xFFFF91D1`).

The lower level (clutch state machine, PWM) was not examined for 20C0; matched functions exist (`0x4C4B2`, `0x495AE`, `0x4A712`) but their fields were not checked.

The upper point bounds of 19D0 `0x8878 / 0x8879` were not found in 20C0. The pedal thresholds by gear are slots 3–12 (§3).

**Gate.** Program arbitration `0x1EC1C` and permission `0x1ED3C` match 19D0 `0x23110` / `0x23230` instruction for instruction; the "code, priority" pair table `0x09A46` differs in two requests (request 1: 20C0 `(0x03, 3)`, 19D0 `(0xFF, 9)`; request 7: `(0x0A, 2)` vs `(0x0A, 3)`). The gate code `0x1EAEE` (pair `0x2300C`): in 19D0, before +/− is touched, the code `[0x8975]` = `0xFE` (branch S) is set and `0x0B` (M) only after an event; in 20C0 **the code `0x0B` is set at once** when `[0x70966] = 0x0B` and `[0xFFFF918C] ≠ 2`, or `[0x70967] = 0x0B` and `[0xFFFF918C] = 2` (`0x1EB88–0x1EBAE`); factory `0x70966` = `0x0B`, `0x70967` = `0x03`. `[0xFFFF918C]` is bits 0–1 of byte 2 of CAN message `0x338` (`0x1CF20–0x1CF2C`, buffer `0xFFFF83E6`); the meaning of the value 2 is not established. Program `0xFFFF914C` = the returned code (`0x18EEC`), the M flag `0xFFFF91AB` = 1 at code `0x0B` or `0x0D` (`0x1EBFC–0x1EC0E`).

**Gear request arbiter** `0x1F200` (pair `0x236C8`): records `0x09F44`, 26 of them (25 in 19D0), a record is 16 bytes `[flag][6×6 table][row][column]`, the first that fires sets the gear `0xFFFF9169`. The new record 5 (`0x09F94`): flag `0xFFFF90E8`, table `0x09E90` (gear + 1), row and column `0xFFFF915F`. The flag is set only by the new function **`0x105DE` — upshift request by engine rpm**: rpm `0xFFFF8D26` not below the word `0x70B20[[0xFFFF915F] − 1]` = 5700 / 5800 / 6000 / 6200 / 8000 / 8000 (`0x10632–0x10644`), with `[0xFFFF9066] ≤ [0x7011B] = 40` (raw ATF, about −10 °C on the 19D0 scale), `[0xFFFF915F]` neither 7 nor 5, `[0xFFFF90A9] = 0`. Called from `0x18F34` when `[0xFFFF9199] ≠ 0`; `[0xFFFF9199]` = 1 with a non-zero byte `0x09A66[([0xFFFF905D] − 1) × 3 + [0xFFFF91A8]]` and bit 1 of the byte `0x70D3C` = `0x12` (`0x1F15C–0x1F17C`). ATF overheat: `[0xFFFF9066] ≥ [0x70131] = 165` (`0x1A868`).

## 8. Protections and voltage

**Turbine monitor** `0x23086` — pair of 19D0 `0x26C84` (document 05 §6), instruction for instruction: turbine `0xFFFF8D5A` not below `[0x70BA8]` (`0x23098 cmp.w`) → fault `0x25` through `0x1534C`. **Threshold `0x70BA8` = 7232** turbine rpm (19D0 `0x8B44` = 6720). Further in the same function `0xFFFF8D18` is compared with `[0x70A92]` = 224 (`0x230AC`) and `[0x70BAA]` = 128 (`0x230FC`): roles not examined. Reaction masks `0x7033C`, 4 bytes per fault, 54 faults (loop `0x1566E`, `moveq #$36`), collected into `0xFFFF8F34`; for fault `0x25` element 36 = `0x00000009` (19D0 `0x30000009`), bit 3 = limp mode.

## 14. Tools

- `python3 tools/egs_tables.py info | scan | shift | programs | dump | diff | verify-shift image.bin` — the layout is chosen by the file size (512 KB = 20C0). `info` prints the code hash `0x08000–0x70000` (reference `28d92179…`), the labels, the 614 tables, the three sums. `shift --turbine` shows the 16 matrices in turbine rpm; `verify-shift` on 20C0 warns that the matrix roles are by shape only and that the real upshift threshold is value + `0xFFFF9143`.
- `python3 tools/gs860_crc.py check | fix` — the three 20C0 sums (layout by file size).
- `python3 tools/make_xdf.py check catalog/gs8604_20c0.json`, `make_xdf.py build catalog/gs8604_20c0.json xdf/GS8604_20C0_Full512K.xdf --en xdf/GS8604_20C0_Full512K_EN.xdf` — the XDF from the catalog, Russian and English (fields `title_en`, `description_en`, `units_en`, `categories_en`); `check` rejects overlaps, duplicates, empty units and addresses outside the image.
- The 20C0 catalog is generated from a 20C0 image by the WOLF4X project generator (all 20 record roots, roles with instruction addresses) and is never edited by hand. Its field roles are only those found in the 20C0 code: the read of the field, the writes of the axis variables, the path to an output.
- The recipes in `recipes/` and documents 02–09 **do not apply** to 20C0: other addresses, other structures. Only the method and the units are shared with 19D0.
