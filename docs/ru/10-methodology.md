# 10 · Методология: как делался реверс и что считается доказанным

## 1. Инструменты

- **capstone** ≥ 5, `CS_ARCH_M68K`, режим `CS_MODE_M68K_040` — иначе не декодируются `muls.l` / `divs.l` (CPU32). Линейный листинг всего образа от `0x400`; пропуски и данные внутри кода видны как мусорные инструкции — это нормально, ориентир — `link.w a6`, `movem.l`, `rts` и таблицы переходов.
- Собственные скрипты на Python без зависимостей: нарезка таблиц по признаку «оси строго возрастают» (`tools/egs_tables.py`), поиск 32-битных указателей на адрес (xref), сравнение образов по таблицам (`diff`).
- Логи DS2 (документ 06) — для проверки.
- Эмуляция CPU32 (Unicorn) для функций, где статический разбор спорен: исполняется настоящий код образа с заданным состоянием RAM. Так 23-24.09.2026 проверены выбор записи 0x34220, нижний автомат ГДТ 0x33F66 и удержание 0x32A38. Второй независимый разбор тем же дизассемблером перепроверяет цепочки и числа.

## 2. Пять шагов, которые не пропускаются

1. **Наблюдение, потом гипотеза.** Не «попробуем поднять параметр», а «машина делает вот это, в логе видно вот это».
2. **Сузить вилку экспериментом.** Пример: коробка уходила в аварийный режим на отсечке ДВС; серия газовок с растущей планкой на нейтрали дала «6613 — норма, ~7008 — срыв».
3. **Найти константу.** Скан образа на u16/u8 в нужном диапазоне. Круглые числа (7000, 9000, 1500) в блоке скаляров — почти всегда калибровочные пороги.
4. **Доказать ссылкой из кода — и записью переменной.** Константа, найденная по значению, ничего не значит, пока не видно, кто её читает **и что за переменная с ней сравнивается**. Этот шаг здесь однажды сделали наполовину: нашли чтение `0x8EEA` в `0x265F4`, увидели сравнение с `0xFFFF906E`, приписали переменной «обороты турбины» по круглому числу — и не проверили, кто пишет `0xFFFF906E`. Проверка показала `raw_ADC × 25250 / 1024` (документ 05 §1). **Правило: для каждой переменной в доказательстве — найти все записи (`move.w d0, $ffffXXXX`), а не только чтения.**
5. **Сверить с логом, включая случаи, когда явления не было.** Если объясняет не всё — гипотеза неполная, и это записывается как открытый вопрос, а не подгоняется.

## 3. Как находились таблицы гидравлики

Прямой поиск ссылок на адрес таблицы (например `0xB974`) в коде ничего не даёт — модуль исполнения читает калибровки через записи-указатели (документ 04 §2). Цепочка: RAM `0xFFFF94F8` → корень `0x3CBCC` → директория наборов `0x3CBBA` → запись `→` поле `→` таблица. Найдено так:

1. В модуле 0x34000+ все обращения к калибровкам имеют вид `movea.l (a5), a0; move.l $NN(a0), -(a7); jsr $2ca2a` — смещение `$NN` = 4 × номер поля.
2. Записи находятся по массивам последовательных указателей в окно калибровки (0x3B372…), их длина — минимальный шаг между уникальными адресами записей (78 × 4 для kind1).
3. Директория наборов — по массиву из 4 указателей на эти массивы (0x3CBBA), корень — по единственной ссылке на директорию (0x3CBCC), RAM-указатель — по записи `0x3CBCC` в `0xFFFF94F8`.
4. Далее для каждого чтения поля `$NN` смотрится, куда идёт результат (фаза, таймер, давление) — так поле получает смысл. Все смещения и адреса кода — в документе 04.

Выбор записи по типу перехода (`0x12FDC`) и набора по классу/направлению (`0x13012`) — из кода 0x343B6 / 0x3425E.

## 4. Воспроизводимость

Каталог 536 таблиц: `python3 tools/egs_tables.py scan stock.bin --csv catalog.csv`. Привязка полей записей к таблицам воспроизводится десятью строками: прочитать `u16 n` и `n` указателей по каждому из четырёх адресов директорий, для каждой записи прочитать `len/4` полей, собрать `(kind, тип, поле) → адрес`. Именно так построены имена в XDF (категории «Гидравлика», «Фазы переключения»).

Все числа в документации проверены по стоковому дампу 19D0 и по дампу Alpina B3 (19D0 620P). Если у вас другая ревизия калибровки 19x0 — `egs_tables.py diff` покажет, что отличается.

## 5. Порядок изменений и A/B

Один шаг — одна сборка — один лог. Не совмещать в первой сборке шаги, которые потом нельзя разделить (например, целевое время скольжения и давление включаемого). Рабочий порядок: (a) откат лишней жёсткости B974 в строках малого момента + целевые времена 3×3 повышения; (b) давление включаемого 2→3 + целевые времена понижения; (c) давление выключаемого 3→2 по Alpina. Критерии оценки лога — документ 06 §4.

## 6. Шкала уверенности, используемая в документах

| Метка | Смысл |
|---|---|
| **доказано / В** | есть чтение в коде, есть запись переменной, есть согласие с логом |
| **С** | роль по коду доказана, величина эффекта оценочная |
| **гипотеза / Н** | структура или число найдены, семантика не подтверждена кодом; тюнить по форме нельзя |
| **опровергнуто** | старая трактовка, снятая кодом: «0x81A0 = фазы соленоидов», «B73E… = время наполнения», «0x8F00/0x8F08 = температура ГДТ», «0xA066… = пороги ГДТ», «0x265F4 = защита турбины 7000 об/мин» (переменные это напряжения, документ 05 §1), «0xAB0C… = карты снятия момента» (это опорное скольжение регулятора ГДТ, документ 04 §9), «0x888C, 0xFFFF9216, 0x901E-0x915E, 0x88B0 = блокировка ГДТ» (это AGS, документ 03 §7), «0xFFFF91B0 = активная программа» и «матрицы 01 / 02 = спорт» (документ 01 §5), «0xFFFF9113 = аварийный режим» (это кикдаун, документ 05 §3), «фаза 4 кончается по таймеру или по флагу 0xFFFF96A6» (документ 04 §5), «ручной порог вверх у отсечки = защита на накате» (документ 02 §5). Прежняя строка этой таблицы «0xAB0C… = карты скольжения ГДТ» как опровергнутое снята: по стороннему реверсу, принятому 23.09.2026, это и есть опорное скольжение регулятора ГДТ |

## 7. Открытые вопросы

- Закрыто 23.09.2026: причина аварийного режима у отсечки это монитор турбины 0x26C84, порог [0x8B44] = 6720, ошибка 0x25 (документ 05 §6).
- Какой канал ШИМ / регистр соответствует какому соленоиду (EDS1…5, MV1…3). Частично закрыто: муфта ГДТ это ШИМ `0xFFFF95BA` и выход `0xFFFFFF34` (по стороннему реверсу, принято 23.09.2026, документ 03 §4).
- Семантика полей kind1 f70 (4×4) и kind3 f65 (6×6), таблиц `0xA066…0xA20A`, `0x917E`, `0x8142`, `0x824A`, слотов 0…11 дескрипторов `0x3AA60`.
- Закрыто 14.10.2026 кодом: формат аргументов команды DS2 `0x06` это `06 <сегмент> <A23..16> <A15..8> <A7..0> <N>` (обработчик 0x18A70, разбор 0x19A4E, документ 01 §6); живой обмен ещё не записан.
- Закрыто 23.09.2026: `0xFFFF918F` это отфильтрованные обороты выходного вала, сдвинутые вправо на 5, а не скорость (документ 02 §3).
- Назначение `0xFFFF90C2` и байтов 21 / 13 / 19 статусного кадра.
- Частично закрыто 08.10.2026: таблицы кодов DS2 это 20C0 `0x707A0` и 19D0 `0x87A8` / `0x87B0` (ошибка монитора турбины 0x25 даёт DS2 0x21, ошибка 0x24 даёт 0x95, документ 05 §6). Открыто: внутренние номера 6–9 в `0x12640`.
- Спорно и не проверено кодом: вход фильтра `0xFFFF8DA4` (`0xFFFF8DA6` или `0xFFFF8DA8`, документ 02 §3), с чем сравнивается 0x8EEA (документ 05 §1).
- Смысл `0xFFFF91CA` (замены PE / PF), роли матриц k5 (PA), k12 (P9), k13 (P7), горные ли ступени `0xFFFF90CD` (гипотеза; с 14.10.2026 цепочка прослежена: пороги зон 0x80D2 × `[0xFFFF918A]` / 100 против `[0xFFFF8D04]`, таблицы 0x98C0 и 0x98E0, каталог 19D0).
- Что подменяют `0xFFFF91B0` / `0xFFFF91B7`, передачу или программу, и как модуль исполнения использует `0xFFFF97EE` (документ 01 §5).
- Условия разрешения полного замыкания 0x32150 и роль состояния 5 нижнего автомата ГДТ.
- Какое сцепление ведёт регулятор времени скольжения (19D0 `0xFFFF974B`; в 20C0 ячейки нет, пара `[0xFFFF93CF]`, закрыто 08.10.2026, документ 11 §15) в каждом виде понижения, записи вида 0, адаптация 0x2AE10.
- Проверить кодом 0x21522: если буфер DME2 непрерывный, `0xFFFF8435` это байт 1 кадра DME2, а не АЦП датчика ATF (документ 03 §6).

## 8. Урок 23.09.2026: AGS приняли за блокировку ГДТ

С 16.09 по 23.09.2026 документ 03 описывал как блокировку ГДТ функции AGS, адаптивного выбора программы: «лесенку» 0x888C, величину `0xFFFF9216`, таблицы 0x901E-0x915E. Роль была выведена из формы (четыре ступени, пороги по педали и скорости) и из того, что функция читает педаль и скорость. Шаг 4 из §2 здесь был сделан наполовину: не проследили, куда идёт результат. Все обращения к `0xFFFF9216` оказались рампами, минимумами и сравнениями в арбитраже программ, в выходы величина не идёт. Настоящая цепочка муфты кончается выходом `0xFFFFFF34` (документ 03 §1). Та же ошибка стояла за прочтениями «0xFFFF91B0 = активная программа» и «матрицы 01 / 02 = спорт»: роль приписали по форме, не проверив, кто выбирает матрицу (таблица 0x24BA4).

Правило, добавленное к §2: для каждой величины, которой приписана физическая роль, пройти по коду до выхода (регистр ШИМ, кадр CAN, решение о передаче или программе). Пока путь до выхода не найден, роль остаётся гипотезой.

## 9. Урок 14.10.2026: таблицы сканера и непрямые читатели

Каталог 19D0 помечал 63 объекта «читателей не найдено». Поиск в два шага находит читателей у 36 из них: сначала 32-битные указатели на начало объекта, затем команды, которые ссылаются на указатель (`pea.l <слот>` каталога указателей 0x9ADC, документ 01 §2-3), или прямой `movea.l #<объект>`. Анализатор, который писал пометки, слоты указателей не проходил. Тот же проход показал, что сканер таблиц (`egs_tables.py scan`: счётчик и следом строго растущие байты) превращал массивы без осей, списки порогов и ряды отдельных констант в таблицы с осями. Девять объектов переописаны, 17 добавлены; например 0x80D0 это список из семи порогов зон, а его «строка данных» это три отдельные константы.

Правило в §2: прежде чем верить таблице сканера, найти её читателя и посмотреть, как код её индексирует. Вызов интерполятора (0x1E680, 0x1E710, 0x1E848, 0x1EB18) значит таблицу с осями. `база + 2 + индекс` или `база + 4 + индекс` значит массив, а байт, который читают по его собственному адресу, это константа.
